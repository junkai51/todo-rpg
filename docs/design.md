# Todo RPG 设计基线

更新：2026-09-10

状态：v0.1 范围已确认；游戏设计有意留白。

本文件是后续开发的单一设计基线。README 只说明如何运行，不另行定义玩法。

## 1. 当前目标与优先级

长期目标：用现实行动驱动 AI GM，使现实任务的完成成为持续 RPG 世界中的进展。

当前版本只让现实任务记录真正可用。电脑浏览器的日常使用最重要，并兼顾 iPhone。采用 TypeScript、React Native 和 Expo 的方向；浏览器优先验证，iPhone 原生适配可以随后补齐。

第一版不实现 GM、Mock GM、奖励预算、游戏状态、Quest、World Chat 或世界生成。不再为了这些未来功能追问或冻结玩法细节。

此前“先 Mock 再立即接真实 LLM”的安排顺延到开始开发 GM 时；它不再是当前现实记录版本的验收条件。

## 2. 已确认的用户行为

- 用户自己按键确认并提交轮次，不按日历时间自动推进。
- 勾选完成立即产生可见反馈，并在本地记录。
- 确认前可以继续添加事项、修改内容、取消完成或取消事项。
- 本轮提交以确认那一刻仍然有效的现实记录为准，不能累加每次勾选动作。
- 本版将“暂时不设计修改、撤回功能”解释为：不实现已提交轮次的修改、撤回或历史回滚；确认前的调整继续保留。
- 未来游戏内容草稿允许重新生成；现在只记录这一决定，不实现生成按钮或确定重生成规则。

“记录完成”“提交现实轮次”“未来确认游戏草稿”是不同的动作。本版只实现前两者。提交现实轮次不代表游戏已经结算。

## 3. v0.1 的最小可用范围

以下是落实上述目标的最小实现约定，不是对未来 Todo 产品形态的限制。

### 现实事项

- 新增事项，标题必填，备注可选。
- 查看未完成、本轮已完成和已提交事项。
- 在提交前修改标题、备注，勾选或取消完成，取消不再需要的事项。
- 显示完成反馈和待提交数量；待提交记录即时持久化。
- 未完成事项在提交后仍留在任务列表，后续更改产生下一轮记录，不修改过去的轮次快照。
- 已提交的完成或取消记录只读。本版不提供将它们重新打开、改写或撤回的操作。
- 暂不做 Project 管理、重复任务、习惯、子任务、日历、提醒、时间追踪或复杂筛选。

### 现实轮次

- 用户查看本轮有效记录后，按一次“提交本轮”。
- 同一事项在一轮中反复修改，最终只提交一份有效快照；被取消的完成不能仍作为完成提交。
- 提交保存轮次编号、提交时间和本轮记录快照，清空本轮待提交集合。
- 没有待提交记录时不创建空轮次。
- 同一份待提交完成记录不能因双击、重试或再次提交而重复进入轮次。
- 历史页面可读已提交快照；它们不随任务列表的后续编辑改变。
- 这里的按钮只提交现实记录，不生成剧情、不计算奖励、不推进 GameState。

### 本地保存

- 关闭再打开或刷新浏览器后，事项、待提交记录和已提交轮次仍在。
- 保存失败必须显示错误；不能把尚未保存的数据提示为已提交。
- 每个浏览器／设备独立保存。本版不做账号、跨设备同步或云端数据库。
- 不需要 API key、LLM 服务或 Python 后端即可使用现实记录。
- 浏览器数据属于当前站点；清除站点数据会删除本地记录。导出／恢复可后续补充。

## 4. 最小模型与模块边界

### Reality Domain：本版实现

- **Task**：现实事项的当前内容、状态与时间信息。
- **Pending Reality Record**：尚未提交的有效现实记录；以事项为单位合并确认前的变化。它不是游戏进展。
- **Reality Turn**：用户主动提交的一批不可变现实记录快照。

当前不强制建立完整的点击审计流水；用户需要的是持久的有效记录，而不是每次反复勾选的历史。未来 RealityEvent 消费者从提交后的现实记录读取信息，不从 UI 点击次数计算进展。

共享领域逻辑不依赖 React、浏览器 API 或数据库驱动。UI 通过本地 repository 执行操作，存储适配器负责原子读写。

### Game Domain：保留边界，暂不实现

- Task 不携带 XP、游戏奖励或与 Quest 的强制一对一映射。
- 只有确认过的完成类现实事件，未来才能由程序产生游戏进展预算。
- 计划、取消、修改等记录只能提供现实上下文，不能单独产生游戏进展。
- GM 只能提出结构化游戏事件；Validator／Rules 校验后，用户确认游戏草稿，才提交 canonical GameEvents 并更新 GameState。
- Narration 是表现，不是事实来源；GameState 与 committed GameEvents 才是事实。
- Game Chat 只读 player-visible state 和 known lore，不读取 hidden state，不可写状态。
- Quest 来源可以结合预设原型、长期现实主题及 LLM 提案，经 promotion／玩家确认，并限制长期任务线数量。
- 记忆分当前状态、近期回合摘要和压缩长期记忆；不把全部原始历史传给模型。
- 固定 engine 与可变 WorldPack 分离；未来自然语言 WorldPackDraft 经过 schema validation 和确认后启用。
- World Builder、Turn Interpreter、Narrator、World Chat 是逻辑角色，不要求部署多个模型或 Agent。
- 未来游戏草稿可重新生成；重生成不允许重复消费现实记录或绕过规则。

本版不创建虚假的 GameState、空 GameMaster 服务、奖励表或占位游戏数据库表。边界保留在本文件和模块依赖方向中，等需要时再实现。

## 5. 技术方向

- 语言与 UI：TypeScript + React Native + Expo，优先运行 Web。
- 浏览器存储：IndexedDB，使用事务保存任务、待提交记录和轮次。
- iPhone 原生存储：SQLite；最小适配已放入工程，原生真机／模拟器验证后续完成，不在浏览器中模拟原生文件数据库。
- 持久化对领域逻辑暴露相同的读取／操作边界；不要为了跨平台共享 UI 而强行共享数据库驱动。
- 本版采用简单本地数据模型，不引入 ORM、全局状态框架、后端、消息队列、向量数据库或完整 event sourcing。
- 依赖版本以实际安装的 package.json 和 lockfile 为准。
- Expo 官方建议 Node LTS；开发环境与安装说明中记录经过验证的运行时。

浏览器选择 IndexedDB 的依据：Expo SQLite 的 Web 支持当前仍标记为 alpha，并需要额外 WASM／跨源隔离配置。浏览器是当前最重要的使用端，因此先使用浏览器原生持久化。参见 [Expo SQLite Web setup](https://docs.expo.dev/versions/latest/sdk/sqlite/#web-setup) 与 [Expo 创建项目要求](https://docs.expo.dev/get-started/create-a-project/)。

## 6. 必须守住的工程行为

1. 修改事项与更新它的待提交记录一起保存；失败时不留下半份状态。
2. 提交轮次时，读取当前有效记录、保存快照和清空对应待提交记录必须原子完成。
3. UI 防双击之外，持久化层也必须防止同一批记录被重复提交。
4. 提交后的快照使用独立数据，不能保留会被后续编辑改变的引用。
5. 非法／空白标题拒绝保存。用户文本作为数据处理，不作为系统指令。
6. 不把提交按钮连接任何游戏状态修改或外部服务。
7. 未来接入 GM 时重新使用冻结的现实快照，而不是读取已经被修改的实时 Task。
8. 所有保存、加载错误明确可见；不把内存演示当成本地持久化成功。

## 7. 第一个 vertical slice

最小验收路径：

1. 在电脑浏览器打开应用，创建两项现实事项。
2. 勾选一项，看到完成反馈与待提交记录。
3. 修改它的备注，再取消完成；确认待提交内容反映最新状态。
4. 新增另一事项并完成；按键提交本轮。
5. 历史只出现确认时有效的快照，不包含已取消的完成结果。
6. 再次按键不会重复提交同一批记录。
7. 未完成事项仍然可用于后续轮次；已提交快照保持原样。
8. 刷新或重新打开，列表、待提交记录与轮次历史保持一致。
9. 全流程不出现 GM 调用、游戏奖励或剧情生成。

先验证这条现实记录路径。将来开始开发 GM 时，先用 Mock 接通提案／校验／确认链路，再接真实 LLM。

## 8. 有意留白

以下内容目前不作决定，也不作为搭建环境的前置条件：

- 现实完成如何换算预算，数值、消耗、上限及结余。
- 角色属性、升级、战斗、装备、经济系统、关系、地点与随机性。
- Quest 数量、阶段、promotion 时机、玩家选择与推进的关系。
- 具体世界题材、角色、语气、WorldPack 字段和存档切换。
- 游戏草稿重生成的次数、可改变的内容、秘密展示时机。
- 模型供应商、prompt、服务架构、Python／FastAPI 接入时机。
- 已提交轮次纠错、回滚、同步及多设备冲突。
